# src/data — 데이터 수집·저장

> 루트 [`CLAUDE.md`](../../CLAUDE.md)의 절대 규칙이 우선한다. 이 문서는 이 폴더 상세.
> 실제 API 응답 검증 결과는 [`docs/KIWOOM_VERIFY.md`](../../docs/KIWOOM_VERIFY.md).

## 데이터 소스 결정

**키움증권 신규 REST API 하나로 통일** — 과거 데이터 수집과 모의투자 실행 모두.

KRX Data Marketplace, 한국투자증권 API, pykrx도 검토했으나 키움 단일 소스로 결정했다.
이미 키움 계좌를 보유하고 있어 별도 계좌 개설이 불필요하고, 모의투자까지 한 파이프라인으로
연결할 수 있기 때문이다.

MCP 서버(`kiwoom-rest-api` npm 패키지)도 등록되어 있지만 **보조 도구**다.
응답 구조를 빠르게 훑어볼 때만 쓰고, 실제 수집은 `src/data/kiwoom/client.py`가 담당한다.

## 키움 REST API 제약 (코드 작성 시 반드시 고려)

| 제약 | 대응 |
|---|---|
| TR별 초당 호출 제한 | 토큰 버킷 + **429 적응**. 429를 맞으면 해당 TR 속도를 절반으로 낮추고 연속 성공 시 회복한다. 재시도만 하면 같은 속도로 계속 부딪힌다 |
| 제한 초과가 HTTP 200 으로도 온다 | `return_code=5` + "초과" 메시지. 상태코드만 보면 놓친다 (ka10099에서 관측) |
| 벌크 엔드포인트 없음 | 종목별 반복 호출 구조. 순회 중 한 종목 실패가 전체를 죽이면 안 된다 |
| 응답값이 전부 문자열 | `"+70000"`, `"1,234,567"` → 공통 파싱 유틸(`src/utils/parsing.py`) 경유 필수 |
| 가격에 등락 부호가 붙음 | 가격류는 `abs_*` 타입으로 파싱. **순매수는 부호가 의미를 가지므로 절대 abs 금지** |
| mock/live base URL 분리 | 환경변수로만 분기. 코드에 URL 하드코딩 금지 |
| 응답이 최신→과거 내림차순 | 저장 전 정렬. 조기 종료 로직이 이 순서에 의존한다 |

## 수집 전략

- 한 번 받은 데이터는 `data/raw/`에 parquet으로 저장. **매번 재수집 금지**
- 이후에는 장마감 후 당일치만 추가하는 **증분 수집**
- 증분은 `storage.upsert()`가 담당: 기존 읽기 → concat → 키 기준 dedup → 정렬 → 덮어쓰기
  - 같은 key가 겹치면 **새 데이터가 이긴다** (수정주가 소급 반영 때문)
- 재실행 안전(idempotent)이 이 폴더의 핵심 계약이다. 깨지면 `tests/test_storage.py`가 잡는다

## 파일 레이아웃

```
data/raw/{TR이름}/{종목코드}.parquet   ← API 응답 원본 (가공 전)
data/processed/{이름}.parquet          ← 지표·라벨까지 계산된 학습용 테이블
```

원본을 남기는 이유: 지표 계산 로직을 바꿔도 **재수집 없이** 다시 만들 수 있다.

## TR 정의 규칙 (`kiwoom/endpoints.py`)

- 실제 응답으로 검증하기 전까지는 `# UNVERIFIED` 주석과 `verified=False`를 유지한다
- 검증이 끝나면 주석을 지우고 `verified=True`, `note`에 함정을 기록한다
- `scripts/collect.py`는 실행 시 미검증 TR을 경고로 출력한다

**현재 상태 (2026-08-27)**: `daily_chart` `stock_info` `investor_flow` `index_daily` `stock_list`
`minute_chart` `index_minute` 7종 검증 완료.
해외 일봉 TR은 **존재하지 않아** 국내상장 ETF로 대체한다.

## 분봉 (`ka10080` / `ka20005`) — 일봉과 계약이 다르다

`scripts/collect_intraday.py` 가 담당한다. 일봉 경로(`collect.py`)와 **분리**돼 있다 —
일봉 수집은 평일 16:00 launchd 에 묶여 있어서 건드리면 그 경로가 같이 위험해진다.

| 차이 | 내용 |
|---|---|
| **이력이 롤링이다** | 약 13개월치만 준다(실측 2026-08-27 기준 2025-08-01까지). 일봉처럼 "나중에 받으면 된다"가 성립하지 않는다 — **안 받으면 사라진다** |
| 키가 `datetime` | `date` 가 아니다. `storage.last_timestamp()` 로 시각까지 기억해야 한다. 날짜로 자르면 하루치를 통째로 다시 받는다 |
| 진행 중인 봉이 온다 | 11:45에 받으면 11:00봉이 미완성이다. `drop_incomplete_bars()` 가 버린다 — 일봉의 `--end-date` 경고에 해당하는 방어인데 여기서는 **자동**이다 |
| 거래대금이 없다 | 일봉 스키마의 `value` 에 해당하는 필드가 응답에 없다 |
| 봉 격자가 고정이 아니다 | 수능일(2025-11-13)은 10:00~16:00, 신년 첫날(2026-01-02)은 6봉이다. **시각을 하드코딩하지 말 것** — 행 순서로 다룬다 |
| 틱범위별로 다른 데이터 | `data/raw/minute60/` 처럼 틱을 디렉터리에 넣는다(`minute_kind()`). 30분봉과 60분봉이 섞이면 안 된다 |

60분봉은 페이지당 900건이라 **종목당 3콜**이면 전체 이력이 끝난다
(146종목 + 지수 2 + ETF = 149건, 실측 10분).

## 유니버스

`scripts/build_universe.py`가 `ka10099`(종목정보 리스트)로 자동 선정해
`configs/universe.yaml`에 쓴다. `config.yaml`의 인라인 목록보다 이 파일이 우선한다.

⚠️ **업종(upName)은 ka10099에 있다.** ka10001(주식기본정보)에는 없으므로 업종은 여기서 받는다.

TR별 관측 속도: `ka10099`는 응답이 커서 0.5 req/s로 제한. 나머지는 3 req/s에서
간헐적 429가 나지만 적응 로직이 흡수한다(146종목 수집 중 9회 발생, 실패 0건).

## 모의투자

구축 완료 — 계좌·주문 TR 은 `endpoints.py` 아래쪽 **매매 TR** 블록에 있고,
어댑터는 [`src/trading/broker.py`](../trading/broker.py) 다.

⚠️ 수집 TR 과 성격이 다르다. **주문 TR 은 계좌 상태를 바꾸고, 잔고 TR 은 조용히 틀린다** —
필드명이 어긋나면 컬럼이 비는 게 아니라 보유수량이 0 으로 읽혀 중복 매수가 나간다.
그래서 `unverified_specs()` 경고와 별개로 `scripts/verify_trading_trs.py` 를 따로 둔다.

`ALL_SPECS` 는 수집 TR 만 담는다. 레이트 리미터에 등록되는 건 `RATE_LIMITED_SPECS`
(수집 + 매매) 이고, 주문 TR 은 1 req/s 로 더 조인다 —
429 재시도가 중복 주문으로 이어지면 안 되기 때문이다.
